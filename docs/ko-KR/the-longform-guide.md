![단축 가이드 참고](../../assets/images/longform/02-shortform-reference.png)
*단축 가이드 - 먼저 읽어보세요*

단축 가이드에서는 기초 설정을 다뤘습니다: 스킬과 커맨드, 훅, 서브에이전트, MCP, 플러그인, 그리고 효과적인 Claude Code 워크플로우의 근간을 형성하는 설정 패턴들. 그것은 설정 가이드이자 기본 인프라였습니다.

이 롱폼 가이드는 생산적인 세션과 낭비적인 세션을 구분하는 기술을 다룹니다. 단축 가이드를 읽지 않으셨다면, 돌아가서 먼저 설정을 완료하세요. 아래 내용은 스킬, 에이전트, 훅, MCP가 이미 설정되어 작동 중임을 전제로 합니다.

여기서 다루는 주제들: 토큰 경제학, 메모리 지속성, 검증 패턴, 병렬화 전략, 재사용 가능한 워크플로우 구축의 복합적 효과. 이것들은 제가 10개월 이상 매일 사용하며 다듬어온 패턴들로, 첫 시간 안에 컨텍스트 부패에 시달리는 것과 몇 시간 동안 생산적인 세션을 유지하는 것의 차이를 만들어냅니다.

단축 가이드와 롱폼 가이드에서 다룬 모든 내용은 GitHub에서 확인할 수 있습니다: `github.com/affaan-m/everything-claude-code`

## 팁과 트릭

### 일부 MCP는 대체 가능하며 컨텍스트 윈도우를 확보해줍니다

버전 관리(GitHub), 데이터베이스(Supabase), 배포(Vercel, Railway) 등의 MCP - 이러한 플랫폼 대부분은 이미 MCP가 본질적으로 래핑하고 있는 강력한 CLI를 가지고 있습니다. MCP는 훌륭한 래퍼지만 비용이 따릅니다.

실제로 MCP를 사용하지 않고도 (그리고 그에 따른 컨텍스트 윈도우 감소 없이) CLI가 MCP처럼 더 잘 기능하게 만들려면, 기능을 스킬과 커맨드로 묶는 것을 고려하세요. MCP가 편리하게 제공하는 도구들을 제거하고 그것들을 커맨드로 전환하세요.

예시: GitHub MCP를 항상 로드하는 대신, 선호하는 옵션으로 `gh pr create`를 래핑하는 `/gh-pr` 커맨드를 만드세요. Supabase MCP가 컨텍스트를 소모하는 대신, Supabase CLI를 직접 사용하는 스킬을 만드세요.

지연 로딩으로 컨텍스트 윈도우 문제는 대부분 해결됩니다. 하지만 토큰 사용량과 비용은 같은 방식으로 해결되지 않습니다. CLI + 스킬 접근 방식은 여전히 토큰 최적화 방법입니다.

## 중요한 내용

### 컨텍스트와 메모리 관리

세션 간 메모리를 공유하려면, 진행 상황을 요약하고 확인한 후 `.claude` 폴더의 `.tmp` 파일에 저장하고 세션이 끝날 때까지 계속 추가하는 스킬이나 커맨드가 최선입니다. 다음 날 그것을 컨텍스트로 사용하여 이전 작업을 이어갈 수 있으며, 각 세션마다 새 파일을 만들어 이전 컨텍스트가 새 작업을 오염시키지 않도록 합니다.

![세션 저장 파일 트리](../../assets/images/longform/03-session-storage.png)
*세션 저장 예시 -> <https://github.com/affaan-m/everything-claude-code/tree/main/examples/sessions>*

Claude가 현재 상태를 요약하는 파일을 만듭니다. 검토하고 필요하면 수정을 요청한 후 새로 시작하세요. 새 대화에서는 파일 경로만 제공하면 됩니다. 컨텍스트 한계에 도달하여 복잡한 작업을 계속해야 할 때 특히 유용합니다. 이 파일에는 다음이 포함되어야 합니다:
- 효과가 있었던 접근 방식 (증거와 함께 검증된)
- 시도했지만 효과가 없었던 접근 방식
- 시도하지 않은 접근 방식과 남은 작업

**컨텍스트 전략적 정리:**

계획이 수립되고 컨텍스트가 정리되면 (현재 Claude Code 플랜 모드의 기본 옵션), 계획에 따라 작업할 수 있습니다. 이는 실행에 더 이상 관련 없는 탐색 컨텍스트가 많이 쌓였을 때 유용합니다. 전략적 압축을 위해 자동 압축을 비활성화하세요. 논리적 간격으로 수동 압축하거나 이를 수행하는 스킬을 만드세요.

**고급: 동적 시스템 프롬프트 주입**

제가 알게 된 한 가지 패턴: 모든 것을 CLAUDE.md(사용자 범위)나 `.claude/rules/`(프로젝트 범위)에만 넣는 것은 매 세션에 로드됩니다. CLI 플래그를 사용하여 컨텍스트를 동적으로 주입하는 방법을 사용하면:

```bash
claude --system-prompt "$(cat memory.md)"
```

이렇게 하면 언제 무엇이 로드될지 더 정확하게 제어할 수 있습니다. 시스템 프롬프트 내용은 사용자 메시지보다 높은 권한을 가지며, 사용자 메시지는 도구 결과보다 높은 권한을 가집니다.

**실용적인 설정:**

```bash
# 일상적인 개발
alias claude-dev='claude --system-prompt "$(cat ~/.claude/contexts/dev.md)"'

# PR 검토 모드
alias claude-review='claude --system-prompt "$(cat ~/.claude/contexts/review.md)"'

# 연구/탐색 모드
alias claude-research='claude --system-prompt "$(cat ~/.claude/contexts/research.md)"'
```

**고급: 메모리 지속성 훅**

대부분의 사람들이 모르는 메모리에 도움이 되는 훅들이 있습니다:

- **PreCompact 훅**: 컨텍스트 압축 전에 중요한 상태를 파일에 저장
- **Stop 훅 (세션 종료)**: 세션 종료 시 학습 내용을 파일에 저장
- **SessionStart 훅**: 새 세션 시작 시 이전 컨텍스트 자동 로드

이러한 훅들을 만들어 레포지토리에 공개했습니다: `github.com/affaan-m/everything-claude-code/tree/main/hooks/memory-persistence`

### 지속적 학습 / 메모리

프롬프트를 여러 번 반복해야 했고 Claude가 같은 문제에 부딪히거나 이전에 들은 것과 같은 응답을 했다면 - 그런 패턴들은 스킬에 추가되어야 합니다.

**문제:** 낭비된 토큰, 낭비된 컨텍스트, 낭비된 시간.

**해결책:** Claude Code가 사소하지 않은 것을 발견하면 - 디버깅 기술, 해결 방법, 프로젝트별 패턴 - 그 지식을 새로운 스킬로 저장합니다. 다음에 비슷한 문제가 생기면 스킬이 자동으로 로드됩니다.

이것을 수행하는 지속적 학습 스킬을 만들었습니다: `github.com/affaan-m/everything-claude-code/tree/main/skills/continuous-learning`

**Stop 훅을 사용하는 이유 (UserPromptSubmit 대신):**

핵심 설계 결정은 UserPromptSubmit 대신 **Stop 훅**을 사용하는 것입니다. UserPromptSubmit은 모든 단일 메시지에서 실행됩니다 - 모든 프롬프트에 지연을 추가합니다. Stop은 세션 종료 시 한 번 실행됩니다 - 가볍고, 세션 중 속도를 떨어뜨리지 않습니다.

### 토큰 최적화

**주요 전략: 서브에이전트 아키텍처**

사용하는 도구와 작업에 충분한 가장 저렴한 모델에게 위임하도록 설계된 서브에이전트 아키텍처를 최적화하세요.

**모델 선택 빠른 참조:**

![모델 선택 표](../../assets/images/longform/04-model-selection.png)
*다양한 일반 작업에 대한 서브에이전트 가상 설정 및 선택 근거*

| 작업 유형                  | 모델   | 이유                                              |
| -------------------------- | ------ | ------------------------------------------------- |
| 탐색/검색                  | Haiku  | 빠르고 저렴하며 파일 찾기에 충분                  |
| 간단한 편집                | Haiku  | 단일 파일 변경, 명확한 지시                       |
| 다중 파일 구현             | Sonnet | 코딩에 최적의 균형                                |
| 복잡한 아키텍처            | Opus   | 깊은 추론 필요                                    |
| PR 검토                    | Sonnet | 컨텍스트 이해, 미묘함 포착                        |
| 보안 분석                  | Opus   | 취약점을 놓칠 여유 없음                           |
| 문서 작성                  | Haiku  | 구조가 단순                                       |
| 복잡한 버그 디버깅         | Opus   | 전체 시스템을 머릿속에 유지해야 함                |

코딩 작업의 90%는 Sonnet을 기본으로 사용하세요. 첫 시도 실패, 5개 이상의 파일, 아키텍처 결정, 보안 중요 코드의 경우 Opus로 업그레이드하세요.

### 검증 루프와 평가

**벤치마킹 워크플로우:**

스킬 유무에 따라 동일한 요청을 하고 출력 차이를 확인하는 방법으로 비교합니다:

대화를 분기하고, 그 중 하나에서 스킬 없이 새 워크트리를 시작하고, 끝에 diff를 보고 무엇이 기록되었는지 확인하세요.

**평가 패턴 유형:**

- **체크포인트 기반 평가**: 명시적 체크포인트 설정, 정의된 기준에 따라 검증, 진행 전 수정
- **지속적 평가**: N분마다 또는 주요 변경 후 실행, 전체 테스트 스위트 + 린트

**핵심 지표:**

```
pass@k: k번의 시도 중 적어도 한 번 성공
        k=1: 70%  k=3: 91%  k=5: 97%

pass^k: k번의 시도 모두 성공해야 함
        k=1: 70%  k=3: 34%  k=5: 17%
```

단순히 작동만 하면 될 때는 **pass@k**를 사용하세요. 일관성이 필수적일 때는 **pass^k**를 사용하세요.

## 병렬화

다중 Claude 터미널 설정에서 대화를 분기할 때, 분기와 원래 대화의 작업 범위가 잘 정의되어 있는지 확인하세요. 코드 변경에서 겹침을 최소화하는 것을 목표로 하세요.

**내가 선호하는 패턴:**

코드 변경을 위한 메인 채팅, 코드베이스와 현재 상태에 대한 질문이나 외부 서비스 연구를 위한 분기.

**임의의 터미널 수에 대하여:**

![병렬 터미널에 대한 Boris의 견해](../../assets/images/longform/07-boris-parallel.png)
*Anthropic의 Boris가 여러 Claude 인스턴스 실행에 대해*

Boris는 병렬화에 대한 팁을 가지고 있습니다. 그는 로컬에서 5개, 업스트림에서 5개의 Claude 인스턴스를 실행하는 것과 같은 것들을 제안했습니다. 저는 임의적인 터미널 수를 설정하는 것을 권장하지 않습니다. 터미널 추가는 진정한 필요성에서 나와야 합니다.

목표는 이것이어야 합니다: **최소한의 병렬화로 얼마나 많은 것을 할 수 있는가.**

**병렬 인스턴스를 위한 Git 워크트리:**

```bash
# 병렬 작업을 위한 워크트리 생성
git worktree add ../project-feature-a feature-a
git worktree add ../project-feature-b feature-b
git worktree add ../project-refactor refactor-branch

# 각 워크트리는 자체 Claude 인스턴스를 얻음
cd ../project-feature-a && claude
```

인스턴스 확장을 시작하고 서로 겹치는 코드를 작업하는 여러 Claude 인스턴스가 있다면, git 워크트리를 사용하고 각각에 대해 매우 잘 정의된 계획을 세우는 것이 필수적입니다. `/rename <이름>`을 사용하여 모든 채팅의 이름을 지정하세요.

![두 터미널 설정](../../assets/images/longform/08-two-terminals.png)
*시작 설정: 왼쪽 터미널은 코딩, 오른쪽 터미널은 질문 - /rename과 /fork 사용*

**캐스케이드 방법:**

여러 Claude Code 인스턴스를 실행할 때 "캐스케이드" 패턴으로 정리하세요:

- 오른쪽의 새 탭에서 새 작업 열기
- 왼쪽에서 오른쪽으로, 오래된 것부터 새것으로 검토
- 한 번에 최대 3-4개 작업에 집중

## 기반 작업

**두 인스턴스 시작 패턴:**

내 워크플로우 관리를 위해, 빈 레포지토리에 2개의 Claude 인스턴스를 열어 시작하는 것을 좋아합니다.

**인스턴스 1: 스캐폴딩 에이전트**
- 기반과 토대를 마련
- 프로젝트 구조 생성
- 설정 구성 (CLAUDE.md, 규칙, 에이전트)

**인스턴스 2: 심층 연구 에이전트**
- 모든 서비스, 웹 검색에 연결
- 상세한 PRD 생성
- 아키텍처 mermaid 다이어그램 생성
- 실제 문서 클립이 포함된 참고 자료 편집

**llms.txt 패턴:**

사용 가능하다면, 문서 페이지에 도달하면 `/llms.txt`를 수행하여 많은 문서 참고 자료에서 `llms.txt`를 찾을 수 있습니다. 이렇게 하면 깔끔하고 LLM에 최적화된 문서 버전을 얻을 수 있습니다.

**철학: 재사용 가능한 패턴 구축**

@omarsar0으로부터: "초기에 재사용 가능한 워크플로우/패턴을 구축하는 데 시간을 투자했습니다. 구축하기 지루하지만, 모델과 에이전트 하네스가 개선됨에 따라 엄청난 복합 효과가 있었습니다."

**투자해야 할 것들:**

- 서브에이전트
- 스킬
- 커맨드

## 에이전트와 서브에이전트 모범 사례

**서브에이전트 컨텍스트 문제:**

서브에이전트는 모든 것을 덤프하는 대신 요약을 반환하여 컨텍스트를 절약하기 위해 존재합니다. 하지만 오케스트레이터에게는 서브에이전트가 부족한 의미론적 컨텍스트가 있습니다. 서브에이전트는 리터럴 쿼리만 알고 있으며, 요청 뒤에 있는 목적은 모릅니다.

**반복적 검색 패턴:**

1. 오케스트레이터가 모든 서브에이전트 반환을 평가
2. 수락하기 전에 후속 질문하기
3. 서브에이전트가 출처로 돌아가 답변을 얻어 반환
4. 충분할 때까지 반복 (최대 3 사이클)

**핵심:** 쿼리만이 아닌 목적 컨텍스트를 전달하세요.

**순차적 단계를 가진 오케스트레이터:**

```markdown
단계 1: 연구 (Explore 에이전트 사용) → research-summary.md
단계 2: 계획 (planner 에이전트 사용) → plan.md
단계 3: 구현 (tdd-guide 에이전트 사용) → 코드 변경
단계 4: 검토 (code-reviewer 에이전트 사용) → review-comments.md
단계 5: 검증 (필요시 build-error-resolver 사용) → 완료 또는 루프 복귀
```

**핵심 규칙:**

1. 각 에이전트는 하나의 명확한 입력을 받고 하나의 명확한 출력을 생성합니다
2. 출력이 다음 단계의 입력이 됩니다
3. 절대 단계를 건너뛰지 마세요
4. 에이전트 사이에 `/clear` 사용
5. 중간 출력을 파일에 저장
